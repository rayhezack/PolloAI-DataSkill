# Section 01：口径维护与冲突裁决

日期：2026-11-26。状态：待 DS 评审。本节对应待拍板事项 OQ-16。

**本节目标：确定最终口径在哪里维护、发现冲突时由谁裁决。**

## 当前现状

现在有两套与取数有关的知识资产：

| 资产 | 目前的内容与用途 |
|---|---|
| 本次建设的 GitHub 知识库 `PolloAI-DataSkill` | 有表卡、维度、指标公式、过滤条件、陷阱和 DS 评审记录，供人和 Coding Agent 检索、取数；目前仍有待评审内容 |
| 数仓生产仓库里的既有登记表 | 有《核心指标口径登记表》《SSOT 规则登记表》和广告口径文档，据交接记录已被看板、告警等引用 |

已有对照记录了 **7 处差异**。例如，同叫“访问注册率”：

- 本库：当日新注册用户数 ÷ 当日访客数。
- 旧登记表：当天登录过的访客数 ÷ 当日访客数，包含老用户。

这两个公式描述不同的事情。若 Agent 只按名称检索，会返回不同答案。该示例用于解释为什么需要裁决机制；具体名称和公式留到用户域评审。

资料来源：[存量知识对照](../governance/legacy_alignment.md)。旧登记表的生产路径是 `ai_workspace/knowledge/data-warehouse/core-metric-registry.md`；本节依据已有对照记录，尚未重新核验生产版本。

## 你现在要做什么

**只需选择下面的维护方式，并指出分工中需要调整的地方。**

| 方案 | 生效后的维护方式 |
|---|---|
| **A：本库维护最终定义（建议）** | 经 DS 及必要的数仓评审后，把最终定义维护在本库。推动旧指标登记表引用这些定义，逐步消除重复维护；数仓底层规则及实现继续在生产仓库维护，并关联到相应定义 |
| B：旧登记表维护最终定义 | 本库作为 Agent 可读的结构化副本；新口径先更新旧登记表，再同步到本库。本库不单独维护另一套生效定义 |

**建议选 A 的原因：** 本库已按“来源表—指标—过滤—评审证据”组织，更适合 Agent 使用，也便于你和同事在 GitHub 逐条评审、追踪变更。

选择 A 只决定维护方向，不等于批准本库现有全部公式；仍须逐域处理具体差异。旧登记表的修改需要与数仓负责人协调，Codex 不会仅凭本节选择就改动生产系统。

## 你需要评审什么

- **维护位置：** 最终定义由本库维护，还是由旧登记表维护？
- **职责分工：** 建议 DS 决定业务语义和指标算法，数仓确认来源表、字段加工及数据问题，Codex 负责文档、结构化配置、SQL 和核验。
- **冲突处理：** 建议先列明两种定义、来源和影响，再由 DS 裁决；需要实现确认的由数仓参与。未裁决时 Agent 应明确说明冲突，已有清晰且已评审的其他指标可以继续使用。
