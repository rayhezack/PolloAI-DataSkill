## 三、内容边界是否符合当前要求

### 已经形成的部分

- **业务口径层：** 支付、用户、创作、广告四个已有域已按 Section 01~13 记录 DS 结论；Agent 作为第五个域纳入，当前只固化指标语义和待办。
- **广告范围：** 本轮只覆盖 Web；大盘 CAC 和渠道 CAC 都使用付费渠道注册，排除自然注册；ROI 已删除。
- **支付范围：** 支付 GMV 含税款和服务费；实收 GMV 仅扣退款；续费金额和续订率分开。
- **执行边界：** 指标状态、SQL 状态、生产证据和历史快照分开记录；没有证据时不把缺失写成 0，也不把候选表写成正式口径。
- **Agent 范围：** 业务定义已确认，App/Web 分端；来源表、字段、SQL 和生产数值等数据基建完成后再补。

### 目前不能宣称的部分

- 不能把 `pilot` 说成全量生产验收；当前没有 `verified` 的表卡、维度或指标。
- 不能把 L4 目录中的 SQL 都说成已验证；模板必须结合状态、参数和证据使用。
- 不能把 `L5_evals` 的结构检查说成 Skill 准确率；Agent 尚未实测，R3 尚未开始。
- 不能用 Agent 的 `draft/TBD` 指标生成生产数值或虚构来源表。

## 四、总审请你重点看这六类问题

1. **分层是否符合你的工作方式：** 是否保留 L1 表卡、L2 指标/维度、L3 术语规则、L4 SQL、L5 评测和治理评审这六个职责边界。
2. **内容是否完整：** 支付、用户、创作、广告、Agent 五个域是否覆盖你希望 Coding Agent 支持的主要问数场景；是否还有缺失业务域或不需要的内容。
3. **状态是否清楚：** 是否接受 `draft → pending_review → pilot → verified → deprecated`；是否接受“条目 pilot”和“整个问数 Skill 通过 R3”是两件事。
4. **Agent 是否保持当前边界：** 先纳入业务定义，来源表和 SQL 等基建完成后再补；在此之前只允许路由、回问和不可用解释。
5. **证据是否足够：** 历史数值是否必须绑定查询日期、观察日、快照日和保存文件；没有实跑证据的内容是否只能作为定义或计划。
6. **交付形态是否合适：** 评审文档、机器可读 YAML、SQL 模板、固定证据和治理记录是否都保留在 GitHub，作为团队协作的唯一版本。
