### 每次交给你的评审包都采用同一形式

1. 开头写中文业务名、完整表名和可点击的相关文件，内部编号仅作为追踪辅助。
2. 每个待决问题写清：业务含义 → 当前算法 → 差异证据 → 建议 → 你的结论。
3. 区分“需要拍板”“已有回复的落地结果”“仅供知晓”，不重复征求已给出的结论。
4. 只有语义或证据发生变化的条目重新评审；发布范围和暂缓项明确列出。

## 5. Codex 后续自行处理的检查项

这些是本次盘点发现的技术和文档问题，先由 Codex 查明与修正；若涉及业务选择，再带证据交 DS 评审。

- **广告分子分母的日期及范围。** Section10已将CAC锁定为全Web成本/同日Web总注册，K-107已有生产证据；LTV=GMV_N/D0注册，ROAS=GMV_N/成本。K-109已写且本地边界检查通过，本轮生产连接超时，待补实跑；ROI已删除。
- **广告表卡残留旧文案。** 投放日主表 purpose 仍称 GMV“自注册日起”，但 key_fields 和评审包写的是投放日起；注册日表与 match_level 仍在部分规则中被称作“错误表”。需要在选表方案确定后统一。
- **广告成熟度的历史解释需复核。** 广告评审包称 2026-10 的 D14 ROI 76.3% 因未成熟而偏低，但按记录的 11-25 核查日，10-31 cohort 的 D14 在 11-14 已满。需核对实际取数日、回刷状态和所用条件，不能直接沿用“10 月下旬未满 14 天”的解释。
- **结构校验尚不覆盖业务一致性。** 当前 lint 检查 Schema、ID、部分引用与评审元数据，未解析 SQL 状态/依赖、未核验所有文字引用，也未检查 pilot 条目的上游状态。支付域在订用户数已为 pilot，但依赖的用户活跃日表仍为 pending_review，需明确依赖的已评审字段范围。
- **实验 SQL 不等于通用问数模板。** K-101 的注册仍读旧注册表；积分直接加全部任务；任务采纳率分母用创作任务数，与当前 L2 的成功任务数不同。需判断是实验专用口径还是迁移遗漏，分别标注或修正；不可因目录叫“verified_queries”就视作已核验。
- **历史证据需标明单位。** P-20 和纠错记录用 58,431 说明重复汇总纠正，它是到期订阅数；支付评审包的 58,120 是到期用户数。两者不能混称“到期人数”。
- **证据来源要补齐。** 本地 7 张表卡的 producer 仍保留“CNB 无权限”旧提示；交接中已记录 CNB API 归档可读。应重新确认访问和实际 SQL，逐表补仓库路径、提交版本及核验查询，不要求用户重复做已完成的登录步骤。

- **旧 SQL 引用要能定位。** 陷阱中仍引用 K-006、K-014、K-018 等，本库没有这些文件。后续须补可定位的来源或纳入经评审的模板，避免检索断链。

## 6. 评审与验收的边界

- R1：确认业务定义、来源表、维度、过滤、去重、时间窗口及允许的临时方案。
- R2：确认代表性问题、应命中的口径/SQL、期望结果及数据截至日期；歧义题的金标可以是“先回问”。
- R3：审阅实际评测结果，确定可用范围和未解决限制。

已有规范对 pilot 的时点有两种表述：R1 后条目可为 pilot，R0 又写 R3 才批准 pilot。建议区分“条目可有限试用”与“整个 Agent 系统通过试用验收”，在治理文档中统一；条目进入 pilot 不等于系统已通过 R3。
