### C6：点位和窗口的区别（回答 DS 的疑问）
两者的基期都是「某天创作过的用户」。区别在于后面那次创作要落在哪个时间范围内：
- **点位 Dn**：恰好在第 n 天又创作，才算再创作。只看那一天。
- **窗口 n 日**：第 1 天到第 n 天里**任意一天**又创作，就算再创作。

例子：用户 11/1 创作（基期），之后 11/3、11/9 又各创作一次。

| 口径 | 看哪天 | 结果 |
|---|---|---|
| D1 点位 | 11/2 | ✗ |
| D7 点位 | 11/8 | ✗ |
| 7 日窗口 | 11/2–11/8 任一天 | ✓（11/3） |

窗口口径一定 ≥ 点位，而且 n 越大窗口值越高。点位适合画留存曲线，窗口适合回答「一周内有没有回来」。按 DS 结论，默认用**点位**，窗口口径要另外显式说明。

## B. 口径冲突裁决（12 条）

每条格式相同：现状冲突 → 选项 → AI 推荐及理由 → DS 结论。

### B-01「App」的定义
- **冲突**：v1 K-003 把 App 定义为 `pay_platform <> 'WEB'`，包含空值和未知端；K-005 起的条目定义为 `IN ('IOS','ANDROID')`。
- **推荐**：统一为 `IN ('IOS','ANDROID')`，`UNKNOWN` 单列展示、不并入 App。K-003 改写为新口径，旧写法标记 deprecated。
  - 理由：Q3 口径说明里写的就是「App=iOS+Android」；单列 UNKNOWN 可以避免对不上数。
- **DS 结论**：采纳

### B-02 日均分母
- **冲突**：K-004 写死 91/92/31 天；K-013、K-014、K-017 用「期间内有数据的天数」。
- **推荐**：统一用**自然日数**，即 `DATEDIFF+1`。「有数据的天数」只用于数据质量检查，不能用于对外数字。
  - 理由：Q3 口径说明写的是「日均按完整自然日数」；动态分母在数据缺天时会虚高日均。
- **DS 结论**：采纳，用**自然日数**

### B-03「付费用户」一词有两种含义
- **冲突**：v1 字典的付费用户是「期间有有效订单的去重用户」（交易口径）；`payment-and-paid-user.md` 的付费用户是「统计日有有效订阅或仍有余额」（权益口径）。
- **推荐**：拆成两个指标，并禁止裸用「付费用户」这个词：
  
  - `M-支付用户数`（交易）
  - `M-有效权益用户数`（存量状态）
  
  用户问到「付费用户」时，AI 必须先回问是哪一种。这与业务总线 V0.1 §2.4 一致。
- **DS 结论**：建议支付用户数。

### B-04 `_dfp` 快照表取哪个分区
- **冲突**：v1 G-01/G-12 写的是 `p_date = MAX_PT(...)`；`development-conventions.md`（verified）规定取昨日分区、禁止 `MAX(p_date)`。
- **推荐**：日常取数用昨日分区。回溯分析显式指定快照日，并在结论里标注「画像截至 yyyy-mm-dd」，Q3 用的是 11/10。删除 v1 里的 `MAX_PT` 写法。
- **DS 结论**：建议取当天的昨日，改变一下写法就行。

### B-05 DAU 的身份键
- **冲突**：v1 K-014 用 paywall 表的 `user_id`（只算登录用户）；`dau-and-identity.md` 用 visitor_id（anon 优先，否则 uid，含未登录访客）；v1 K-009 用埋点 `uid`。
- **推荐**：拆成两个指标：
  - `M-登录DAU`（user_id）
  - `M-访客UV`（visitor_id）

  一期的转化漏斗（曝光率、创作渗透）统一以「登录 DAU」为分母；访客 UV 只用于访问和获客类指标。
- **DS 结论**：采纳，拆成两个指标。

### B-06「注册新用户」两套定义
- **冲突**：v1 G-08 和 Q3 §2.3.2 用的是「期间内注册」，即 Q3 新客指 Q3 内注册；Q3 口径说明的人数段用的是「当天注册」。
- **推荐**：拆成两个维度，**不允许再用「新用户」这个裸词**：
  
  - `D-当日新客`（注册日 = 行为日）
  - `D-期间新客`（注册日 ≥ 期间起点）
  
  注册日期未知的统一单列，不并入新老。
- **DS 结论**：采纳，分成当日新和期间新客。

### B-07 续费率的口径
- **现状**：v1 K-019 和 Q3 都用「到期 cohort，[到期−1, 到期+7] 天内下一周期为 RENEW」，只在成熟周期上计算；业务总线 V0.1 要求「30 日再次支付」单独命名为复购率。
- **推荐**：`M-7日续费率` 采用上述 cohort 口径，并明确 UPGRADE、重置、降级不计入 RENEW。30 日复购率单独作为一个指标，一期不建。
- **DS 结论**：建议采取这个口径没问题。

### B-08 GMV 的名称和含义
- **现状**：GMV = `SUM(amount_received_usd)`，是实收金额，不扣退款，是否含税未声明，排除 API。
- **推荐**：指标名定为「GMV（实收，USD）」，并带固定声明：「不扣退款、API 盘外、不等于净收入或利润」。净收款、毛利放进 open_questions，owner 是财务。
- **DS 结论**：建议继续维持支付GMV的名称；如果是扣除退款的，可以改为实收GMV。

### B-09 业务日时区
- **现状**：Q3 口径说明写的是「event_time 已是东八区」；业务总线 V0.1 第 3 问把时区列为待拍板项。
- **推荐**：一期按 UTC+8 自然日执行，所有交付物标注时区；时区本身记入 open_questions。
- **DS 结论**：采纳，UTC+8.

### B-10「活跃」分母两套
- **冲突**：v1 缺口 #9 记录的问题：K-009 用埋点当日去重 uid，K-014 用 ads 表的 `is_active`，两者同叫 DAU 但数值不同。
- **推荐**：以 ads 表 `is_active` 作为 `M-登录DAU` 的唯一来源；埋点 uid 只用于入口渗透类指标，命名为「埋点活跃 UV」以示区别。
- **DS 结论**：采纳，直接用 `mc_prd.default.ads_pollo_transaction_paywall_user_daily_dip`的is_active。



### B-11 创作「任务」的粒度
- **冲突**：Q3 和 v1 用 `creation_task.record_id` 计「有效任务」；业务总线 V0.1 要求请求、供应商任务、产物三层粒度分开。
- **推荐**：R1 阶段查清 `record_id` 对应哪一层，指标按实际粒度命名，例如「有效生成请求数」。在查清之前，统一称为「有效任务数（creation_task 口径）」。
- **DS 结论**：请求、产物等根本就不是你这么理解的，参考下方SQL：

```SQL
SELECT 
    cast(created_time as date),
    user_id,
    MIN(cast(created_time as datetime)) min_created_time,
    count(distinct record_id) task_cnt, -- 创作任务数
    count(distinct case when submit_time is not null then record_id end) submit_task_cnt, -- 请求任务数
    count(distinct case when is_success_by_output = 1 then record_id end) success_task_cnt, -- 成功创作任务数
    count(distinct case when adopted_output_cnt_3d > 0 then record_id end) adopted_task_cnt, -- 采纳任务数
    SUM(success_output_cnt) success_output_cnt, -- 成功输出作品数
    SUM(adopted_output_cnt_3d) adopted_output_cnt_3d, -- 成功输出作品数
    SUM(credit_consume) credit_consume -- 创作消耗积分
from mc_prd.dwd_pollo_creation_task_dip
where 
    p_date between '${start_date}' and '${end_date}'
    and is_valid_task = 1
    AND lower(platform_type) = 'web'
group by
    cast(created_time as date),
    user_id;
```



### B-12 贡献拆解方法
- **现状**：Q3 用 LMDI 拆 GMV 的乘法因子，用两因子 Shapley 拆「结构×效率」，相对差用 %，率的差用 pp。
- **推荐**：写入 `L3_analysis_patterns.md`：
  - 乘法链（DAU × 率 × 客单）用 LMDI；
  - 二因子结构/效率拆解用 Shapley；
  - 贡献只解释算术变化，不代表因果；
  - 不同人群或时间轴的贡献不能相加。
- **DS 结论**：采纳。
