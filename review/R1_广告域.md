### 2. CAC 的分母

口径文档的定义是：

- **CAC** = 消耗 ÷ 同窗口的投放注册用户数（`reg_user_cnt_dN`）；看至今累计时用 `_all`。
- **LTV_N** = `gmv_usd_dN` ÷ `reg_user_cnt_dN`。
- **ROAS_N** = `gmv_usd_dN` ÷ 消耗。

你给的「ROI = LTV ÷ CAC」和它一致：两边用同一个注册分母，约掉后就是 ROAS。2026-10 的 CAC：D0 口径 $1.23，`_all` 口径 $1.18。

## 二、第 3 版的问题已由代码和文档回答（仅供知晓）

| 第 3 版的问题 | 答案 | 来源 |
|---|---|---|
| `reg_user_cnt_dN` 是什么 | 注册日 − 投放日 ≤ N 天的投放注册用户数，不含自然量 | 生产 SQL |
| GMV 窗口 | 付款日 − 投放日 ∈ [0, N]，是毛额：不扣退款，剔除风控单和 0 元单，含 App 商店付款 | 生产 SQL |
| WEB 安装 | 只有 App 有安装数，Web 为空；CPI 只算 App | 口径文档 |
| 消耗和注册错位 | 主表的钱和人都落在投放日，按日可以看趋势，决策按周或按月 | 口径文档 |

**另外补进知识库三条硬规则**：

1. **统计截到 T-2，不是 T-1**：昨天的 App 花费当天还没结清。
2. **D_N 只用满 N 天的日期**：未满的是部分值，不是空值，混进去会拉低回收率。
3. **回本和 CAC 只算人和钱对得上的平台**：Web 的 google、bing、yahoo、naver，App 的 meta、asa、tiktok；App 的 google 从 2026-04-01 起算。

历史成熟度解释纠正（2026-11-27）：第 3 版称 10 月 D14 的 76.3% 因未成熟而偏低，证据不足。按 11-25 核查日，10-31 cohort 的 D14 已于 11-14 满窗；该数字不能以“未成熟”解释。且这只是旧 GMV/消耗比率，不是 Section09 新 CAC 下 LTV/CAC 恒等式的验证。
